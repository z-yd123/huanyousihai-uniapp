# 业务规则实现说明（含材料缺陷与待确认项处理）

本文记录三件事：佣金引擎的落地口径、材料自身的一处矛盾及取舍、待确认问题（Q-xx）的默认取值与改动成本。

---

## 一、佣金引擎落地口径

### 1.1 输入

```java
record Subject(String orderNo, Long newMemberId, Long referrerId,
               int directSeq, Long referrerReferrerId)
```

- `referrerId`：直推人（新会员的推荐人）
- `directSeq`：**新会员是这个直推人的第几个直推**（按人独立计数，从 1 开始）
- `referrerReferrerId`：间推人（直推人的推荐人），最多取到第二级

### 1.2 拨比规则

| 直推序号 | 直推奖 | 间推奖 | 合计 | 受益人数 |
| --- | --- | --- | --- | --- |
| 1 | 10000 分 | 10000 分 | 20000 分 | 2 |
| 2 | 10000 分 | 10000 分 | 20000 分 | 2 |
| ≥3 | 20000 分 | 0 | 20000 分 | **1** |

拨比规则从 `hys_config` 读取（`payout.direct_first_two` / `payout.indirect_first_two` / `payout.direct_after`），但三者的**合计被服务端强制锁定为 20000**：

```java
if (rule.directFirstTwo() + rule.indirectFirstTwo() != rule.total()) → 拒绝保存
if (rule.directAfter() != rule.total())                            → 拒绝保存
```

### 1.3 中断计佣（不静默少发）

| 异常 | 判定 | 处理 |
| --- | --- | --- |
| 直推人缺失 | `referrerId == null` | 整单中断，差额全额记 `hys_payout_gap(reason=GAP_REFERRER_MISSING)` |
| 间推人缺失但本该发间推奖 | `indirectAmount > 0 && referrerReferrerId == null` | 整单中断，记 `hys_payout_gap(reason=GAP_INDIRECT_MISSING)` |

**为什么是整单中断而不是「至少把直推奖发了」**：材料 §6.2 第 7 条明确「禁止按 100 元静默出账」，否则账面会长期少拨 100 元而无人发现。中断后由管理端「异常对账」页人工补绑 + 重算，账实才可能对齐。

### 1.4 合规断言（每次结算都跑）

```java
assert settlement.totalAmount() == 20000;              // 不多拨不少拨
assert 受益人去重后数量 == 明细条数;                     // 同一人不出两条
assert 每条 amount() > 0;
assert 每条 depth() <= 2;                              // 没有第三级
assert 若存在间推奖 → 明细恰好 2 条;
```

## 二、材料自身的矛盾与取舍（重要）

### 2.1 矛盾点

`AGENT.md` 同一节内出现互斥表述：

| 位置 | 表述 |
| --- | --- |
| §6.1 表格第 3 行 | 「第 3 个及以后：直推人 200 元，间推人 **0 元**」 |
| §6.1 表格下方注 | 「**受益人恒为 2 人**」 |
| §6.3 伪代码断言 | `assert beneficiaryCount(order) == 2` |
| §8.3 用例 | 「我推荐第 3 人升级 398 → 我得 200，我的上级 **0**」 |
| §8.3 用例 | 「任意订单（正常业务）→ **受益人恰好 2 人**」 |

第 3 个直推起，200 元已被直推人全额拿走，间推人拿 0 —— 此时不可能同时满足「受益人恰好 2 人」（除非给间推人记一条 0 元明细，而 0 元明细既违反「金额必须为正」，也会污染明细列表的 `amount > 0` 过滤）。

### 2.2 采用的口径

按**可执行的 §6.1 表格 + §8.3 前四条用例**实现：

| 情形 | 直推 | 间推 | 合计 | 受益人数 |
| --- | --- | --- | --- | --- |
| 第 1、2 个直推 | 100 | 100 | 200 | 2 |
| 第 3 个起 | 200 | 不计发（无 0 元记录） | 200 | 1 |

合规断言相应改为三条可同时成立的约束：

1. 合计恒等于 200 元（不多拨不少拨）
2. 层级 ≤ 2（永无第三级）
3. **有间推奖时恰好两条明细**（直推 + 间推）

单测 `CommissionEngineTest.PayoutCases` 里三个 case 直接覆盖：`firstDirect`、`secondDirect`、`thirdDirectGetsAll`（断言 `beneficiaryCount == 1` 且 `total == 20000`）。

### 2.3 对业务的实际影响

- 会员推荐的第 3 个人起，其上级不再从这单获利 —— 这正是「两级封顶 + 200 元拨比固定」的必然结果，也符合「防止无限拉人套利」的监管意图。
- 若业务方最终认定「受益人必须恒为 2 人」，则只有两种改法：给间推人记 0 元（被「金额必须为正」否决），或把第 3 单起的 200 元拆成 100/100（违反 §8.3 用例「我得 200」）。**两种改法都与材料其他条款冲突**，因此维持现口径，并把矛盾如实上报（见 §2.1 表格）。

> 这条记录也是本次交付的一部分：材料缺陷不隐藏、不擅自「圆」过去，而是给出可执行选择 + 影响面。

## 四、几个容易被忽略的实现细节

### 4.1 直推序号怎么算

`hys_member.direct_seq` 在注册时写入：`countDirect(referrerId) + 1`。这个值**一旦写入不再变化**，因为它标识的是「该会员在其推荐人名下的第几位」，不随后续人员变动而重排。

序号错一位就会导致 100/100 与 200/0 判错，所以注册逻辑与 `countDirect` 都必须是同一事务内的快照。

### 4.2 推荐路径 `referrer_path`

形如 `,1,2,3,`（含自身，便于 `like ',1,2,3,%'` 前缀匹配统计全部后代）。团队人数口径：

```sql
-- 团队人数 = 全部后代（排除本人）
select count(1) from hys_member c
where c.referrer_path like concat(m.referrer_path, m.member_id, ',%')
  and c.member_id <> m.member_id
```

早期版本漏了 `c.member_id <> m.member_id`，导致团队人数把本人算进去（+1）。该缺陷已修复，接口签名也改成 `countTeam(path, excludeId)` 显式传排除项，避免再犯。

### 4.3 提现为什么先冻结再出款

提现走 `hys_fund_apply` 人工审核：

1. 申请时 `balance -= amount; frozen += amount`（冻结）
2. 审核通过：`frozen -= amount`，落 `WITHDRAW` 流水（含手续费）
3. 审核驳回：`frozen -= amount; balance += amount`（解冻）

这样在审核期间余额不可再被花掉，也不会出现「审核中还能把钱转走」的双花。

### 4.4 退款为什么要三步

`refund` 在同一事务里做三件事：退余额（`REFUND` 流水）→ 回冲佣金（`COMMISSION_REVERSE` 流水，把已发的钱从受益人余额扣回）→ 回滚库存。少任何一步都会导致账实不符，所以不允许「只退款不回冲佣金」的快捷路径。

### 4.5 会员 JWT 为什么带 `token_version`

无状态令牌无法主动吊销。改密 / 登出 / 管理员停用时把 `hys_member.token_version + 1`，拦截器比对令牌里的版本号与库里的版本号，不一致即 401。这样既保留了无状态校验的性能，又拿到了「立即失效」的能力。

### 4.6 前端为什么不参与算价

`ProductCard.price` / `ProductDetail.price` 由服务端按当前会员身份算好（VIP 且未过期取 VIP 价，否则普通价）。下单时前端只传 `productId + quantity`，**不传价格**。这样即使篡改请求也无法用 VIP 价买普通商品，也无法反过来。
